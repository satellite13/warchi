# MEMORY

## Warchi Release Playbook

Для `warchi` слово **«релизим»** означает полный релизный цикл:

1. Коммитим все готовые изменения.
2. Поднимаем версии везде, где они должны быть синхронизированы для релиза.
3. Дописываем `CHANGELOG.md`.
4. Ставим git-тег релиза.
5. Пушим коммит(ы) и тег(и) в удалённый репозиторий.

### Пошаговый чеклист с командами

1. Проверить рабочее состояние:
   - `git status --short`
   - убедиться, что в релиз входят только нужные изменения

2. Зафиксировать изменения:
   - `git add <нужные файлы>`
   - `git commit -m "..."` (релизный или предрелизный коммит)

3. Поднять версии:
   - обновить `version` в `package.json` (и связанные версии в соседних проектах, если релиз это требует)
   - при изменении зависимостей/версий зафиксировать `package-lock.json`

4. Обновить `CHANGELOG.md`:
   - добавить секцию `## [X.Y.Z] - YYYY-MM-DD`
   - заполнить `Added/Changed/Fixed`
   - обновить ссылки внизу (`[Unreleased]`, `[X.Y.Z]`)

5. Прогнать базовые проверки перед релизом:
   - `npm run build`
   - `npm run test` (если применимо)

6. Сделать релизный коммит:
   - `git add CHANGELOG.md package.json package-lock.json <прочие релизные файлы>`
   - `git commit -m "Release X.Y.Z."`

7. Поставить аннотированный тег:
   - `git tag -a vX.Y.Z -m "Release vX.Y.Z."`

8. Опубликовать в удалённый репозиторий:
   - `git push`
   - `git push --tags`

9. Проверить, что релиз опубликован:
   - `git log --oneline -1`
   - `git tag --list "vX.Y.Z"`
   - проверить наличие тега и коммита в remote

## Notes

- Если пользователь не уточнил иное, релиз подразумевает именно все шаги выше, а не только `git push`.
