# Миграция диаграммы на новую версию нотации

Нужно ли давать возможность переводить существующую диаграмму на новую версию нотации (например, после copyNotation).

## Суть

Диаграмма привязана к нотации по `notationId`. При появлении новой версии нотации (другой id, например 1.1.0) может понадобиться перевести существующую диаграмму на эту версию, чтобы она использовала новые компоненты/связи/оформление без пересоздания диаграммы.

## Сложность

В `attrs` диаграммы хранятся привязки к компонентам и связям по их **id**. В новой версии нотации у компонентов/связей **другие id** (при copyNotation создаются новые записи). Простая смена `diagram.notationId` сломает диаграмму: старые id в attrs не будут находиться в новой нотации. Нужна **миграция с перемаппингом**: заменить старые id компонентов/связей на соответствующие id в новой версии нотации. Для этого нужно знать соответствие «старый id → новый id» (например, из момента копирования нотации или из хранимой таблицы маппинга).

## Варианты

### 1. Да, давать возможность мигрировать

- Отдельная операция вроде «Перевести диаграмму на нотацию 1.1.0» (или «Использовать новую версию нотации»).
- **Бэкенд**: эндпоинт типа `POST /api/v1/diagrams/{id}/migrate-notation` с телом `{ targetNotationId }`. Проверка: целевая нотация должна быть «потомком» текущей (например, создана через copyNotation от текущей), чтобы был или может быть построен маппинг id. Перемаппинг componentId/relationId в `attrs` по этому маппингу, обновление `diagram.notationId`.
- Если при копировании нотации маппинг не сохраняли — можно хранить его при copyNotation (таблица `notation_copy_mappings` или аналог) или разрешать миграцию только «в том же запросе», когда маппинг ещё есть в памяти.

### 2. Нет, не давать

- Для новой версии нотации пользователь создаёт новую диаграмму и заново расставляет элементы. Проще реализация, но хуже UX при больших диаграммах.

## Рекомендация

Возможность мигрировать диаграмму на новую версию нотации **имеет смысл** (лучший UX, меньше ручной работы). Реализационно удобно: при copyNotation сохранять маппинг «исходная нотация + id компонентов/связей → новая нотация + новые id», затем при миграции диаграммы использовать этот маппинг для перезаписи ссылок в `attrs` и смены `notationId`. Альтернатива — разрешать миграцию только «сразу после копирования» в одном потоке (без постоянного хранения маппинга), но тогда нельзя будет мигрировать диаграмму позже.

## Компоненты/связи, удалённые в новой версии нотации

При миграции с нотации 1 на нотацию 2 часть компонентов или связей могла быть удалена в нотации 2. На диаграмме при этом остаются экземпляры, ссылающиеся на старый componentId/relationId, для которых в новой нотации **нет соответствия** (нет в маппинге, т.к. при копировании их не копировали). Что с ними делать?

### Варианты

1. **Удалить с диаграммы**  
   Экземпляры узлов и рёбер, чей компонент/связь отсутствует в новой нотации, удалять из `attrs` при миграции. Узлы и связи исчезают с диаграммы. Плюс: диаграмма остаётся консистентной. Минус: пользователь может не ожидать потери элементов; нужно явно предупреждать («На диаграмме 3 узла используют компоненты, удалённые в новой версии. Они будут удалены.»).

2. **Оставить как плейсхолдеры**  
   Экземпляры не удалять; в новой нотации для них нет компонента/связи, поэтому при отрисовке показывать плейсхолдер («Удалённый компонент», «[Removed]» или серый блок). Позиции и связи сохраняются; пользователь может позже заменить плейсхолдер на новый компонент или удалить вручную. Плюс: ничего не теряется «тихо». Минус: нужна поддержка в UI и в данных (например, флаг или специальный id «unknown component» в attrs).

3. **Запретить миграцию при наличии таких экземпляров**  
   Если на диаграмме есть хотя бы один экземпляр, ссылающийся на компонент/связь, отсутствующий в целевой нотации, миграцию не выполнять, вернуть ошибку с перечислением («Миграция невозможна: на диаграмме используются компоненты X, Y, которых нет в нотации 2. Удалите их с диаграммы или выберите другую нотацию.»). Плюс: пользователь сам решает, что делать. Минус: лишний шаг (сначала почистить диаграмму, потом мигрировать).

4. **Выбор при миграции**  
   Перед миграцией показывать предупреждение: «В новой версии нотации удалены компоненты A, B. Экземпляры на диаграмме: удалить / оставить как плейсхолдеры». В запрос миграции добавить параметр, например `orphanHandling: "remove" | "placeholder"`. Плюс: гибко. Минус: сложнее API и UI.

### Рекомендация

- **По умолчанию** разумно **удалять** экземпляры с отсутствующим компонентом/связью (вариант 1) и **обязательно показывать предупреждение** перед миграцией: сколько узлов и рёбер будет удалено, перечень имён компонентов/связей. Так диаграмма после миграции всегда валидна, а пользователь предупреждён.
- **Опционально** добавить параметр `orphanHandling: "remove" | "placeholder"` (вариант 4): при `"placeholder"` сохранять экземпляры без маппинга и отображать их как плейсхолдер (требует доработки отрисовки и, при необходимости, хранения «сирот» в attrs — например, с пустым или специальным componentId).

То же самое применимо к **связям (relations)**: рёбра, привязанные к связи, удалённой в новой нотации, либо удалять, либо оставлять как плейсхолдер (линия без типа/стиля или с подписью «Удалённая связь»).

## Изменение relation rules в новой версии нотации

В новой версии нотации могли измениться **relation rules** (правила «какие пары компонентов разрешены для данной связи»). После перемаппинга id рёбра на диаграмме ссылаются на пару (sourceComponentId, targetComponentId) и relationId в нотации 2. Если для этой связи в нотации 2 правило (fromComponent, toComponent) удалили или изменили, рёбро перестаёт соответствовать правилам — оно **невалидно** с точки зрения новой нотации.

### Что делать с невалидными рёбрами

- **Удалить с диаграммы**: рёбра, нарушающие relation rules целевой нотации, удалять из attrs при миграции. Плюс: диаграмма консистентна с нотацией. Минус: пользователь теряет связи; нужен предпросмотр и предупреждение («Следующие N рёбер не соответствуют правилам новой нотации и будут удалены: …»).
- **Оставить как плейсхолдеры**: не удалять; при отрисовке/валидации помечать такие рёбра как «нарушает правила» (подсветка, иконка, тултип). Пользователь может потом переподключить или удалить вручную. Требует поддержки в UI.
- **Запретить миграцию**: если есть хотя бы одно невалидное ребро, возвращать ошибку с перечислением. Пользователь сначала правит диаграмму или правила нотации.
- **Выбор при миграции**: параметр вроде `invalidEdgesHandling: "remove" | "keep"` и предупреждение перед миграцией с перечислением затронутых рёбер.

Рекомендация та же, что и для удалённых компонентов/связей: по умолчанию **удалять** невалидные рёбра с явным предупреждением в preview; опционально — параметр для режима «оставить» (плейсхолдер/подсветка). В **preview** перед миграцией показывать и сирот по компонентам/связям, и рёбра, нарушающие relation rules.

## Детали реализации (при выборе варианта 1)

- **Хранение маппинга**: таблица вида `notation_copy_mappings (source_notation_id, target_notation_id, source_entity_type, source_entity_id, target_entity_id)` или JSON в отдельной сущности, заполняемая при copyNotation.
- **Миграция attrs**: в `diagram.attrs` (JSON) заменить все вхождения старых componentId/relationId на новые по маппингу. Для ссылок без соответствия в маппинге — в зависимости от выбранной политики: удалить экземпляр из attrs (и связанные рёбра) или оставить с пометкой/плейсхолдером. После перемаппинга проверить каждое ребро на соответствие relation rules целевой нотации; невалидные рёбра — удалить или оставить по политике `invalidEdgesHandling`.
- **Перед миграцией (preview)**: по маппингу вычислить список экземпляров узлов/рёбер, которые станут «сиротами» (нет в целевой нотации); по relation rules целевой нотации — список рёбер, которые станут невалидными. Вернуть оба списка в ответе «preview» или показать в UI с предупреждением.
- **Права**: проверять, что пользователь может редактировать диаграмму и что целевая нотация доступна (view/edit).
