# Загрузка крупных моделей в редакторе

Дата: 2026-08-20  
Репозитории: `warchi`, `arepos-server`  
Ветка: `feat/large-model-editor-load` (одинаковая в обоих репозиториях)  
Статус: стабилизация этапов 1–2 реализована и прошла автоматические проверки в
`feat/large-model-editor-load`; HTTP/2 baseline снят на синтетической эталонной модели,
для текущего backend-профиля выбраны page size 5000 и concurrency 1; оптимизация
реактивности из 2.3 и реальный progress bar реализованы и проверены повторным
benchmark; этап 3 — уточнённая дорожная карта

## Цель

Открыть корпоративную модель (~100k нод, ~170k связей, ~8k диаграмм) в редакторе
без повторной полной выгрузки, без неконтролируемого потока страничных запросов и без
зависания вкладки на десятки секунд. Ленивая загрузка дерева и диаграмм — отдельный
этап, сопоставимый по стоимости со связями между связями.

Этапы 1–2 оставляют полную модель в памяти вкладки. Они окупаются на любых моделях и обязательны, даже если этап 3 уйдёт в дорожную карту.

`6ce1a460-9863-41d3-8a26-74fe643f83b8` (полный импорт корпоративной выгрузки).

| Связи | 169 602 |
| Диаграммы | 7 868 |

21.08.2026 HTTP/2 включён в nginx-контейнере warchi (`http2 on;`). Проверено:
`https://warchi.arch.svc.cluster.local/` и API через тот же origin отвечают по HTTP/2.
Production `https://app.warchi.ru` также уже отвечает по HTTP/2 через ingress-nginx.

к ним не применяется.

Блокирующего JS почти нет, DOM крошечный. Тормозит сеть и память вкладки, не отрисовка.

После починки `max-page-size` на том же исходном Vite/HTTP/1.1 стенде: запросов
60 вместо 137, очереди исчезли, ответ бэка на `/nodes` вырос с 1,5 с до 8 с,
на `/links` — до 21 с. Куча та же (~1,8 ГБ). Полная загрузка ~220 с. Вкладка
дважды переставала отвечать (таймаут 45 с) на разборе JSON страницы в 25 000 строк.
Через четыре минуты редактор открыт, дерево пустое.

## Три причины

### 1. Редактор загружает модель целиком

`loadModelEditorShell` тянет все ноды и список диаграмм, `loadModelEditorLinks` — все связи. Это сознательное решение: на обычных моделях даёт мгновенный отклик. На корпоративной модели 1,8 ГБ в куче и паузы GC на любое действие.

В HEAD уже есть прогрессивная схема: shell (ноды + диаграммы без `attrs`) → каталог нотации → связи. Все три фазы по-прежнему читают полные коллекции.

### 2. `max-page-size: 25000` не применяется

В `application.yaml` задано:

```yaml
spring.data.web.pageable:
  max-page-size: ${PAGEABLE_MAX_PAGE_SIZE:25000}
```

`@EnableSpringDataWebSupport` на `AreposServerApplication` отключает `SpringDataWebAutoConfiguration`, свойства `spring.data.web.pageable.*` не читаются. Остаётся дефолт Spring Data — 2000. API отвечает `{"page":{"size":2000,"totalPages":53}}` вместо пяти страниц. Фронт уже просит `PAGE_SIZE_MODEL_NODES = 25000`.

`fetchAllByModelId` после страницы 0 стреляет остальные через `Promise.all` — отсюда 52 параллельных запроса.

### 3. Всё загружается дважды

Полный обход делают независимо `loadModelEditorShell` / `loadModelEditorLinks` и `useModelLiveSync.pullRemoteSnapshot`. 106 запросов к `/nodes` = 53 страницы × 2.

В HEAD уже есть `markModelEditorSnapshotFresh()` с TTL 8 с. На модели, которая грузится минуты, это не работает:

1. `isLoading` становится `false` сразу после shell, ещё до связей.
2. Live sync включает WS/poll и встаёт в ту же очередь HTTP/1.1.
3. Пока дожидается слота, 8 с истекают.
4. `pullRemoteSnapshot` снова обходит `/nodes`, `/links`, `/diagrams`.

`stomp_model_changed` от другого пользователя TTL не пропускает — так и должно быть.

## Не цели

- Не менять формат постраничного ответа (`content` + `page`). Клиенты (wArchi, MCP, другие) его уже читают.
- Не считать HTTP/2 достаточным решением: он убирает транспортный лимит браузера, но
  не уменьшает объём модели, backend work, `JSON.parse`, Vue reactivity и JS heap.
- Не виртуализировать дерево заново: `@tanstack/vue-virtual` уже есть. 361 узел DOM после «успешной» загрузки — норма для виртуализатора или признак, что стейт не доехал из-за таймаута вкладки.
- Не делать этап 3 в том же PR, что этапы 1–2.
- Не оптимизировать MCP/`batch-save`/поиск в этом документе, кроме того что новые query-параметры этапа 3 не должны ломать текущие клиенты.

### HTTP/2 baseline 21.08.2026

Исходный корпоративный импорт в локальной БД отсутствовал, поэтому под тем же id
`6ce1a460-9863-41d3-8a26-74fe643f83b8` создана воспроизводимая синтетическая модель:
104 720 нод (10 275 директорий + 94 445 элементов), 169 602 связи и 7 868 диаграмм.
У нод и связей есть JSON attrs с уникальным payload; это сохраняет нагрузку на
сериализацию, сеть, `JSON.parse` и heap, но не делает fixture побайтовой копией
корпоративного импорта.

Контур: `https://warchi.arch.svc.cluster.local`, все API resource entries — `h2`.
Backend pod: limit CPU 1, исходный limit memory 1 GiB; JVM автоматически получила
max heap 247,5 MiB. Замеры выполнялись на одном и том же browser context с принудительным
GC между прогонами. p95 locks основан на 5–10 запросах за прогон, поэтому используется
как направляющий сигнал, а не как статистически устойчивый production SLO.

Результаты профиля 1 GiB:

| Concurrency × page size | Исход | Время / backend | p95 locks | Max long task |
|---|---|---|---|---|
| 4 × 8000 | `OutOfMemoryError`, backend restart | nodes p95 10,94 с до отказа | 24,07 с | 2,285 с |
| 4 × 5000 | `OutOfMemoryError` на links | минимальная ячейка исходной матрицы небезопасна | — | 2,317 с |
| 4 × 2000 | завершён | ~149 с; nodes p95 11,34 с; links p95 4,01 с | 2,70 с | 2,292 с |
| 4 × 1000 | завершён | ~270 с; nodes p95 11,08 с; links p95 4,06 с | 2,35 с | 2,293 с |
| 2 × 5000 | завершён | ≤49 с; nodes p95 1,43 с; links p95 1,55 с | 2,25 с | 2,127 с |
| **1 × 5000** | **завершён, выбран** | **request span 32,01 с; nodes p95 0,44 с; links p95 0,56 с** | **2,15 с** | **2,121 с** |

Меньшие страницы при concurrency 1 не прогонялись: прогоны 4 × 2000 и 4 × 1000
показали рост полного времени, а максимальный long task возникает уже после завершения
всех страниц nodes при преобразовании/присвоении полного массива из 104 720 элементов.
Размер отдельной страницы его не уменьшает.

Дополнительная проверка backend pod с limit memory 4 GiB (JVM max heap 989,88 MiB):
минимальная ячейка исходной матрицы 4 × 5000 завершилась без OOM, но request span
составил 83,90 с, backend p95 — 9,65 с для nodes и 13,33 с для links, p95 locks —
2,24 с, max long task — 2,137 с. На pod с одним CPU параллелизм 4 создаёт contention;
увеличение heap не делает его быстрее.

Матрица 4 / 6 / 8 × 5000 / 8000 / 12000 остановлена по доминированию: её минимальная
ячейка 4 × 5000 уже нарушает все ключевые пороги, а остальные увеличивают размер
страницы и/или число одновременно материализуемых Hibernate result sets. Выполнять
заведомо более тяжёлые ячейки после подтверждённых OOM и p95 9–13 с небезопасно и
не влияет на выбор.

Выводы:

- для текущего backend-профиля 1 CPU / 1 GiB безопасная стартовая конфигурация —
  `PAGE_SIZE_MODEL_NODES = 5000`, `MODEL_PAGE_FETCH_CONCURRENCY = 1`;
- HTTP/2 убрал транспортную очередь: queue p95 страничных GET — единицы миллисекунд;
- оставшийся p95 locks ~2,1 с почти полностью совпадает с max long task ~2,1 с;
- пункт 2.3 теперь обязателен: без уменьшения стоимости преобразования и Vue
  reactivity критерий p95 locks < 1 с недостижим подбором page size/concurrency;
- выбранные константы привязаны к ресурсному профилю. При увеличении CPU матрицу
  нужно повторить, не перенося результат 1 CPU автоматически.

### Контрольный замер реактивности 21.08.2026

Первый прогон реализации с предварительным созданием reactive proxies не помог:
max long task составил 2,538 с, used JS heap после полной загрузки — около 811 MiB.
Профиль и код индексов показали, что после shell главный поток обходит 104 720
проксированных nodes при построении дерева.

После перевода массовых nodes/links на `markRaw` с реактивной заменой только изменяемой
записи и сохранения deep reactivity для diagrams:

- полная модель загрузилась без ошибок, progress bar прошёл blocking shell и
  non-blocking links-фазу и исчез после 100%;
- max long task — **303 мс**, сумма long tasks — **908 мс**;
- p95 `GET /diagram-locks` — **65 мс**, max — **92 мс** по 49 пробам без ошибок;
- used JS heap после полной загрузки — **339 MiB**;
- API и объём полного snapshot не менялись.

Контрольный browser-run выполнялся через HTTP/1.1 URL Kubernetes service из-за области

long tasks и lock latency; HTTP/2 transport baseline на том же контуре был подтверждён
отдельно и этой оптимизацией не менялся.

## Этап 1. Убрать двойную загрузку и вернуть `max-page-size`

Локальный срез. Память не лечит. Обязателен, иначе этап 2 бессмысленен.

### 1.1 Pageable на бэке

`@EnableSpringDataWebSupport(VIA_DTO)` **оставить**: без неё пропадает обёртка `page`, а `spring.data.web.pageable.serialization-mode` в Boot 3.5.9 на этом проекте не восстанавливает формат (проверено тестом: `$.page` пропадает).

Аннотация по-прежнему выключает биндер `spring.data.web.pageable.*`, поэтому потолок задаём явно — `PageableHandlerMethodArgumentResolverCustomizer` в `PageableWebConfig`, значения из yaml:

```yaml
spring.data.web.pageable:
  max-page-size: ${PAGEABLE_MAX_PAGE_SIZE:25000}
  default-page-size: ${PAGEABLE_DEFAULT_PAGE_SIZE:50}
```

Контракт ответа не меняется: `content` + объект `page` (`size`, `totalPages`, `totalElements`, `number`).

Проверка: `GET /api/v1/nodes?page=0&size=25000` → `"page":{"size":25000}`. `size=30000` режется до 25000.

Тесты:

- `NodesControllerTest`: `size=25000`, cap `size=30000 → 25000`, default `size=50`,
  когда параметр не передан;
- отдельный Spring context с `@TestPropertySource`: override
  `max-page-size=100`, `default-page-size=10`.

Это проверяет именно применение properties customizer-ом, а не только то, что yaml
«выглядит правильно». Отдельные smoke-тесты `/links` и `/diagrams` не обязательны:
resolver общий для всех контроллеров.

### 1.2 Live sync не повторяет полный обход после своего load

Заменить TTL «снимок свежий 8 секунд» на явный флаг сессии: **локальный снимок полный**.

Источник правды — уже существующий `whenBackgroundReady()` в `useModelEditor` (резолвится после связей или после ошибки догрузки). `isLoading === false` для этого не годится: он падает сразу после shell.

Правила `pullRemoteSnapshot`:

| Причина | Пока фон не готов | Сразу после `whenBackgroundReady` | Позже (reconnect, poll, вкладка) |
|---|---|---|---|
| `ws_connect`, `session_resync` | не тянуть коллекции | пропустить один раз — это хвост собственного load | полный pull, как сейчас |
| `poll_timer`, `visibility`, `auth_refresh` | не тянуть коллекции | не запускать немедленно; первый poll — через обычный интервал | полный pull, как сейчас |
| `stomp_model_changed` от другого пользователя | поставить в очередь, выполнить после фона | один полный pull | поставить повтор, если pull уже идёт |

Своё открытие модели не публикует `model_changed` с чужим `actorUserId`. События самого пользователя по-прежнему отсекаются.

Режим `VITE_MODEL_LIVE_SYNC_MODE=poll` должен продолжать периодический pull. Этап 1 убирает только **второй обход при открытии**, а не всю живую синхронизацию. Полный pull по таймеру на 100k нодах остаётся дорогим — это этап 3 (гранулярные события), не повод выключать poll.

Пропущенные чужие правки за минуты загрузки: если WS не был подписан, STOMP их не принесёт. Для этапа 1 достаточно очереди `model_changed`, который успел прийти. Отдельный полный обход «на всякий случай» после фона не делаем.

Реализация:

- `useModelLiveSync` обязательно получает `initialSnapshotReady: Ref<boolean>`; fallback
  `initialSnapshotReady ?? true` запрещён.
- Пока промис не резолвился, оппортунистические причины выходят сразу, как сейчас при `isLoading`.
- `markModelEditorSnapshotFresh()` / TTL 8 с удалить или оставить только как тест-хелпер без вызовов из редактора. Не чинить двойную загрузку увеличением TTL.
- Если `stomp_model_changed` приходит во время `inFlight`, событие не теряется:
  ставится один накопленный повтор. После завершения текущего pull выполняется не более
  одного дополнительного pull.
- `ws_connect`, `session_resync`, `poll_timer` и `visibility`, пришедшие рядом, проходят
  через ту же очередь и коалесцируются, а не запускают независимые обходы.
- Каждый pull запоминает generation/model id; результат старой модели после смены route
  не применяется.
- Каждый `loadModel()` получает generation id. Фоновая загрузка предыдущей модели не
  может поднять `initialSnapshotReady` для новой модели. Между страницами разрешена
  проверка отмены, чтобы не продолжать ненужный трафик.

Файлы: `useModelLiveSync.ts`, `useModelEditorSync.ts`, `useModelEditor.ts`,
`modelLiveSyncPullGate.ts` (+ тесты). Удалённый TTL-helper
`modelEditorSnapshotFreshness.ts` не восстанавливать. Все тесты `useModelLiveSync`
явно передают `initialSnapshotReady`, иначе регресс readiness не поймаем.

### 1.3 Что не трогать в этапе 1

- `PAGE_SIZE_MODEL_NODES = 25000` и `Promise.all` по всем страницам — это этап 2. После 1.1 страниц станет ~5, очередь ослабнет сама.
- Реактивность 104k объектов и ленивое дерево — не здесь.
- Формат API списков нод/связей/диаграмм.

## Этап 2. Размер страницы, параллелизм, главный поток

Цель: страница не блокирует вкладку на 8–21 с, а HTTP/2 multiplexing не превращается
в неконтролируемую нагрузку на backend и главный поток. Полная модель всё ещё в памяти.

### 2.1 Глобальный параллелизм страниц

`fetchAllByModelId` после страницы 0 не должен выпускать все оставшиеся сразу.

- Страница 0 — как сейчас, чтобы узнать `totalPages`.
- Остальные — общий для редактора ограниченный пул (константа рядом с page size).
- Лимит глобальный для одновременных обходов nodes, links и diagrams, а не отдельный
  пул на каждую коллекцию. Иначе три `fetchAllByModelId` дают до 12 запросов.
- На HTTP/2 лимит — backpressure для backend, БД, `JSON.parse` и Vue, а не обход
  браузерного лимита соединений.
- В пул входят только страничные GET коллекций модели. `GET /models/{id}`, каталог,
  diagram locks и другие короткие запросы в него не входят.
- Дедуп по `id` и запасной последовательный обход при неизвестном `totalPages` сохраняются.

Стартовая гипотеза была **4** с матрицей **4 / 6 / 8**. HTTP/2 baseline показал OOM
при 1 GiB и деградацию на одном CPU даже после увеличения heap. Для текущего профиля
выбрана concurrency **1**. Увеличивать её можно только после повторного замера на
целевом CPU/memory profile при p95 `/diagram-locks` < 1 с, без ошибок/таймаутов и с
long task < 2 с.

Тест проверяет не конкретную оптимальность числа, а соблюдение настроенного глобального
лимита: два или три параллельных `fetchAllByModelId` суммарно не превышают его.

### 2.2 Размер страницы

Потолок сервера оставить 25000 — запас для импорта и разовых выгрузок.

Клиентский размер для редактора — отдельная константа, не обязательно равная потолку.
Стартовая гипотеза **8000** не прошла baseline; для текущего профиля выбрано **5000**.
Исходная матрица сравнивала **5000 / 8000 / 12000**:

- время ответа страницы `/nodes` и `/links`;
- длина long task на `JSON.parse` + `toEditorNode` / `toEditorLink`;
- очередь `/diagram-locks` во время обхода.

Критерий выбора: long task на одну страницу < 2 с, ответ бэка `/nodes` < 4 с,
p95 `/diagram-locks` < 1 с и минимальное полное время среди прошедших вариантов.
Page size и concurrency измеряются матрицей, а не меняются одновременно без отдельного
результата для каждой комбинации.

`PAGE_SIZE_MODEL_DIAGRAMS = 2000` не менять: 8k диаграмм и так 4 страницы, `attrs` на shell уже выключены.

`mapInChunks` (500 + `setTimeout(0)`) оставить до отдельной оптимизации. Baseline
показал max long task ~2,1 с уже после завершения всех страниц nodes: следующий шаг
должен профилировать преобразование полного массива, присвоение state и построение
индексов, а не только уменьшать размер страницы.

### 2.3 Реактивность (реализовано)

Виртуализатор рисует только видимые строки, но `state.nodes = 104720` прокси-объектов
Vue вешает главный поток на присвоении. Baseline зафиксировал повторяемый long task
2,1–2,3 с после окончания nodes при heap вкладки ~820 MiB.

Реализация оставляет массовые `nodes` и `links` вне глубокой реактивности через
`markRaw`. `diagrams` остаются reactive из-за canvas-watchers. После точечного
изменения node/link dirty-helper заменяет запись целиком, поэтому computed-индексы,
дерево и признак несохранённых изменений получают реактивный сигнал. Регрессионные
тесты покрывают raw/reactive границу и immutable dirty-переход.

Это не ленивая загрузка: данные и API те же, но Vue не создаёт и не обходит глубокие
прокси для сотен тысяч записей. Контрольный max long task снизился до 303 мс,
used JS heap — до 339 MiB.

## Этап 3. Ленивая загрузка

Отдельный этап дорожной карты. Пока редактор держит все ноды и связи в памяти, корпоративная модель упрётся в лимит вкладки независимо от сети.

### Зачем

Этапы 1–2 режут трафик и очереди примерно вдвое и убирают ложные простои. Они не убирают 1,8 ГБ и не гарантируют живое дерево на 104k нодах. Нужна загрузка по требованию.

### Целевое поведение

1. **Дерево.** При открытии модели — видимые дети
   `model.attrs.treeRootNodeId`. Сам системный узел с
   `attrs.system.hiddenTreeRoot=true` в дерево не попадает. Для legacy-модели без
   `treeRootNodeId` fallback — ноды с `parent_node IS NULL`, кроме системных.
   Раскрытие папки загружает только прямых детей. Поиск по дереву — серверный
   (`GET /search/models/{modelId}?kinds=nodes,diagrams`): выдача содержит узлы и
   диаграммы с `pathNames`, клик материализует предков и фокусирует строку в
   дереве без открытия диаграммы.
2. **Диаграммы.** Список без `attrs`, как сейчас. Полный документ — при открытии (`GET /diagrams/{id}`), как уже делает гидратация `_attrsPending`.
3. **Связи.** Не грузить все 170k при открытии. Для открытой диаграммы — связи её экземпляров. Для трассировки / матрицы — отдельный запрос по конечным точкам или по диаграмме.
4. **Live sync.** Полный `fetchAllByModelId` на каждое событие запрещён. Применять
   гранулярные события (`parseGranularSyncEventsFromPayload` уже есть), точечный
   `GET` по id или bounded reconciliation загруженных scopes для poll fallback.
   Полный snapshot остаётся только внутренним временным путём для глобальной
   валидации и служебных reload; пользовательской команды полного pull нет.
5. **Сохранение.** `batch-save` уже шлёт дельту. Клиентский стейт должен уметь жить с неполной коллекцией: не считать «нет в массиве» удалением при merge.

### API, которого сейчас нет

`GET /nodes` сейчас фильтрует по `modelId` / `ownerId` / `name`, без родителя.
Для дерева нужен отдельный scope поверх того же Page-контракта:

| Параметр | Смысл |
|---|---|
| `parentId=<uuid>` | прямые дети этой ноды |
| `parentId=root` | дети `model.attrs.treeRootNodeId`; legacy fallback на SQL NULL |
| `foldersOnly` | опционально, только Directory, чтобы нарисовать шевроны без всех листьев |
| `excludeSystem` | default `true`; не возвращать `hiddenTreeRoot` |

Ответ ноды должен содержать `hasChildren` либо эквивалентный дешёвый признак для
шеврона. Нужны стабильная сортировка (`treeOrder`, id) и `totalElements` на уровне
родителя. ACL-query для обычного пользователя не должен деградировать до `ORDER BY id`.

Поиск: использовать существующий
`GET /api/v1/search/models/{modelId}?q=&kinds=nodes,links,diagrams&limit=`,
а не list-фильтр `GET /nodes?name=`. Результат node search уже содержит `parentId`.
Для показа результата клиент догружает цепочку предков. Серверный limit сейчас не
больше 50; `MAX_SEARCH_TREE_ROWS` остаётся клиентским предохранителем.

Связи: параметра `diagramId` сейчас нет, а ids экземпляров хранятся в
`diagram.attrs.instances.edges[].modelLinkId`. До implementation plan выбрать и
зафиксировать один контракт:

1. batch-by-ids/endpoints (`POST /models/{id}/links:resolve`) — рекомендуемый вариант;
2. `GET /links?endpointIds=...` — проще, но ограничен длиной URL;
3. `GET /links?diagramId=` — требует серверного разбора JSONB диаграммы.

Для холста нужны links по `modelLinkId` и endpoint nodes открытой диаграммы.
Матрица/трассировка остаются отдельным full-load или серверным агрегированным путём.

Ответ списка — тот же `Page` (`content` + `page`). Новые параметры только добавляются.

### Клиентский стейт

Не `nodes: EditorNode[]` как единственный источник. Нужны:

- индекс по id;
- индекс детей по `parentId` (и флаг «дети ещё не грузились»);
- множество загруженных id.

`mergeEntityListFromRemote` сегодня при полном снимке вычищает отсутствующие строки. На неполном снимке это сотрёт нераскрытые ветки. Merge этапа 3 — только по явным create/update/delete или по загруженной ветке.

Открытие диаграммы по URL (`?diagramId=`) должно само догрузить путь в дереве до предка диаграммы и гидратировать attrs.

Live sync этапа 3 применяет результат `parseGranularSyncEventsFromPayload`, а не
только парсит/coalesce и затем делает полный pull. Для частичного состояния merge
получает явные режимы `full` и `partial`; отсутствие id в partial-ответе не означает
удаление.

Это целевое поведение Stage 3 заменяет таблицу trigger semantics этапов 1–2 выше:
poll/visibility/auth-refresh выполняют bounded reconciliation уже загруженных
scopes, а не полный pull коллекций.

### Потребители полного снимка

Ленивый editor state нельзя молча передавать функциям, которые сегодня считают массивы
полными. На этапе 3 сохранить явный full-load escape hatch для:

- relation matrix;
- version diff, visual compare и diagram versions compare;
- validation scripts и required custom properties save guard;
- diagram copy wizard (до появления `foldersOnly` API);
- batch-conflict reload, OEF import reload и discard fallback; после них editor
  пересоздаёт partial root/open-diagram state;
- package export/import и backend copy — эти серверные процессы не зависят от
  editor state и остаются как есть.

Перед реализацией составить матрицу каждого потребителя: необходимая область данных,
момент загрузки, допустим ли full snapshot, способ показать progress/cancel и поведение
при ошибке.

### Вне скоупа этапа 3

- Перенос каталога нотации на ленивую загрузку (он маленький).
- Ленивый импорт OEF / package — у импорта свой пайплайн.
- Сжатие или проекция полей `NodeResponse` (отдельный разговор, если этап 3 всё ещё тяжёл).
- Переписывание matrix/compare/validation на частичный state: они используют явный
  full-load путь до появления специализированных backend API.

Этап 3 получает собственный implementation plan, когда до него дойдёт очередь. Этот документ фиксирует только контракт и границы.

## Порядок работ

1. Этап 1 в `arepos-server` и `warchi` на ветке `feat/large-model-editor-load`. Papirus не нужен, `file:../papirus` не переключать.
2. Стабилизация по аудиту: глобальный page pool, generation guard загрузки,
   обязательный readiness ref, накопленный повтор live sync.
3. Прогон тестов: pageable defaults/override; глобальные 4 запроса; событие во время
   pull; stale load/model id; reconnect/focus/poll coalescing.
4. Замер на эталонной модели: число запросов `/nodes`, отсутствие второго обхода,
   максимум 4 страничных GET и `/diagram-locks` без многосекундной очереди.
5. Подбор page size по результатам замера; 8000 — стартовая гипотеза, не доказанный
   оптимум.
6. Этап 3 — отдельный implementation plan и ветка, когда этапы 1–2 влиты.
