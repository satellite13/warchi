# Загрузка крупных моделей в редакторе

Дата: 2026-08-20  
Репозитории: `warchi`, `arepos-server`  
Ветка: `feat/large-model-editor-load` (одинаковая в обоих репозиториях)  
Статус: черновик на ревью

## Цель

Открыть корпоративную модель (~100k нод, ~170k связей, ~8k диаграмм) в редакторе без повторной полной выгрузки, без очереди HTTP/1.1 на мелочи вроде блокировок диаграмм и без зависания вкладки на десятки секунд. Ленивая загрузка дерева и диаграмм — отдельный этап, сопоставимый по стоимости со связями между связями.

Этапы 1–2 оставляют полную модель в памяти вкладки. Они окупаются на любых моделях и обязательны, даже если этап 3 уйдёт в дорожную карту.

## Замеры 20.08.2026

Локальный стенд: wArchi 0.21.4, arepos-server 0.13.2, модель `6ce1a460-9863-41d3-8a26-74fe643f83b8` (полный импорт корпоративной выгрузки).

| | |
|---|---|
| Ноды | 104 720 (94 444 элемента + 10 275 папок) |
| Связи | 169 602 |
| Диаграммы | 7 868 |
| Запросов к `/api/` | 137 (106 `/nodes`, 8 `/links`, 5 `/diagrams`) |
| Скачано | 166 МБ |
| JS heap | 1 821 МБ из лимита 4 192 МБ |
| Длинных задач | 5, суммарно 5,7 с |
| Узлов DOM | 372 |

Время уходит в очередь браузера, не в бэкенд: клиент выпускает до 52 запросов сразу, HTTP/1.1 держит шесть соединений на хост. `GET /diagram-locks` ждал 19 с в очереди ради ответа за 67 мс.

Блокирующего JS почти нет, DOM крошечный. Тормозит сеть и память вкладки, не отрисовка.

После починки `max-page-size` на стенде: запросов 60 вместо 137, очереди исчезли, ответ бэка на `/nodes` вырос с 1,5 с до 8 с, на `/links` — до 21 с. Куча та же (~1,8 ГБ). Полная загрузка ~220 с. Вкладка дважды переставала отвечать (таймаут 45 с) на разборе JSON страницы в 25 000 строк. Через четыре минуты редактор открыт, дерево пустое.

## Три причины

### 1. Редактор загружает модель целиком

`loadModelEditorShell` тянет все ноды и список диаграмм, `loadModelEditorLinks` — все связи. Это сознательное решение: на обычных моделях даёт мгновенный отклик. На корпоративной модели 1,8 ГБ в куче и паузы GC на любое действие.

В HEAD уже есть прогрессивная схема: shell (ноды + диаграммы без `attrs`) → каталог нотации → связи. Все три фазы по-прежнему читают полные коллекции.

### 2. `max-page-size: 25000` не применяется

В `application.yaml` задано:

```yaml
spring.data.web.pageable:
  max-page-size: ${PAGEABLE_MAX_PAGE_SIZE:25000}
```

`@EnableSpringDataWebSupport` на `AreposServerApplication` отключает `SpringDataWebAutoConfiguration`, свойства `spring.data.web.pageable.*` не читаются. Остаётся дефолт Spring Data — 2000. API отвечает `{"page":{"size":2000,"totalPages":53}}` вместо пяти страниц. Фронт уже просит `PAGE_SIZE_MODEL_NODES = 25000`.

`fetchAllByModelId` после страницы 0 стреляет остальные через `Promise.all` — отсюда 52 параллельных запроса.

### 3. Всё загружается дважды

Полный обход делают независимо `loadModelEditorShell` / `loadModelEditorLinks` и `useModelLiveSync.pullRemoteSnapshot`. 106 запросов к `/nodes` = 53 страницы × 2.

В HEAD уже есть `markModelEditorSnapshotFresh()` с TTL 8 с. На модели, которая грузится минуты, это не работает:

1. `isLoading` становится `false` сразу после shell, ещё до связей.
2. Live sync включает WS/poll и встаёт в ту же очередь HTTP/1.1.
3. Пока дожидается слота, 8 с истекают.
4. `pullRemoteSnapshot` снова обходит `/nodes`, `/links`, `/diagrams`.

`stomp_model_changed` от другого пользователя TTL не пропускает — так и должно быть.

## Не цели

- Не менять формат постраничного ответа (`content` + `page`). Клиенты (wArchi, MCP, другие) его уже читают.
- Не включать HTTP/2 на локальном прокси как «решение». Очередь — следствие 52 параллельных запросов, не отсутствие HTTP/2.
- Не виртуализировать дерево заново: `@tanstack/vue-virtual` уже есть. 361 узел DOM после «успешной» загрузки — норма для виртуализатора или признак, что стейт не доехал из-за таймаута вкладки.
- Не делать этап 3 в том же PR, что этапы 1–2.
- Не оптимизировать MCP/`batch-save`/поиск в этом документе, кроме того что новые query-параметры этапа 3 не должны ломать текущие клиенты.

## Критерии успеха

Эталон — та же корпоративная модель на локальном стенде, Chrome, `PerformanceResourceTiming` по `/api/` + `performance.memory`.

| После этапа | Запросы `/nodes` при открытии | Повторный полный обход live sync | Очередь на `/diagram-locks` | Дерево | JS heap |
|---|---|---|---|---|---|
| Сейчас (0.21.4, page size 2000) | ~106 | да | десятки секунд | пустое / вкладка мертва | ~1,8 ГБ |
| Этап 1 | одна серия страниц, не две | нет, кроме чужого `model_changed` | не стоит за обходом нод | корни видны после shell | без изменений |
| Этап 2 | меньше и короче, чем 5×25k | нет | мелочь проходит между страницами | корни видны, вкладка отвечает | без изменений или ниже за счёт меньших пиков JSON |
| Этап 3 | ветка / открытая диаграмма, не вся модель | инкрементально | нет очереди от полной модели | раскрытие папки грузит детей | существенно ниже 1,8 ГБ |

«Вкладка отвечает» = обращение к ней не падает по таймауту 45 с во время разбора очередной страницы.

## Этап 1. Убрать двойную загрузку и вернуть `max-page-size`

Локальный срез. Память не лечит. Обязателен, иначе этап 2 бессмысленен.

### 1.1 Pageable на бэке

Снять ручную аннотацию с `AreposServerApplication`:

```kotlin
@EnableSpringDataWebSupport(pageSerializationMode = PageSerializationMode.VIA_DTO)
```

Перенести режим сериализации в свойство, чтобы снова заработала автоконфигурация:

```yaml
spring.data.web.pageable:
  serialization-mode: via_dto
  max-page-size: ${PAGEABLE_MAX_PAGE_SIZE:25000}
  default-page-size: ${PAGEABLE_DEFAULT_PAGE_SIZE:50}
```

Контракт ответа не меняется: `content` + объект `page` (`size`, `totalPages`, `totalElements`, `number`). На стенде это уже проверено, фронт правки не заметил.

Проверка: `GET /api/v1/nodes?modelId=…&page=0&size=25000` должен вернуть `"page":{"size":25000,…}`, а не 2000. Потолок по-прежнему 25000: `size=30000` режется до 25000.

Тест — контроллерный или slice: запрос с `size=25000` не ужимается до 2000. Не полагаться только на то, что yaml «выглядит правильно».

### 1.2 Live sync не повторяет полный обход после своего load

Заменить TTL «снимок свежий 8 секунд» на явный флаг сессии: **локальный снимок полный**.

Источник правды — уже существующий `whenBackgroundReady()` в `useModelEditor` (резолвится после связей или после ошибки догрузки). `isLoading === false` для этого не годится: он падает сразу после shell.

Правила `pullRemoteSnapshot`:

| Причина | Пока фон не готов | Сразу после `whenBackgroundReady` | Позже (reconnect, poll, вкладка) |
|---|---|---|---|
| `ws_connect`, `session_resync` | не тянуть коллекции | пропустить один раз — это хвост собственного load | полный pull, как сейчас |
| `poll_timer`, `visibility`, `auth_refresh` | не тянуть коллекции | не запускать немедленно; первый poll — через обычный интервал | полный pull, как сейчас |
| `stomp_model_changed` от другого пользователя | поставить в очередь, выполнить после фона | один полный pull | как сейчас |

Своё открытие модели не публикует `model_changed` с чужим `actorUserId`. События самого пользователя по-прежнему отсекаются.

Режим `VITE_MODEL_LIVE_SYNC_MODE=poll` должен продолжать периодический pull. Этап 1 убирает только **второй обход при открытии**, а не всю живую синхронизацию. Полный pull по таймеру на 100k нодах остаётся дорогим — это этап 3 (гранулярные события), не повод выключать poll.

Пропущенные чужие правки за минуты загрузки: если WS не был подписан, STOMP их не принесёт. Для этапа 1 достаточно очереди `model_changed`, который успел прийти. Отдельный полный обход «на всякий случай» после фона не делаем.

Реализация:

- `useModelLiveSync` получает `whenBackgroundReady` (или `initialSnapshotReady: Ref<boolean>`).
- Пока промис не резолвился, оппортунистические причины выходят сразу, как сейчас при `isLoading`.
- `markModelEditorSnapshotFresh()` / TTL 8 с удалить или оставить только как тест-хелпер без вызовов из редактора. Не чинить двойную загрузку увеличением TTL.
- `inFlight` и смена `modelId` — как сейчас.

Файлы: `useModelLiveSync.ts`, `useModelEditorSync.ts`, `useModelEditor.ts`, `modelEditorSnapshotFreshness.ts` (+ тесты). Тесты `useModelLiveSync` сейчас мокают `isModelEditorSnapshotFresh → false` и тем самым всегда тянут снимок при `isLoading=false`; их надо перевести на новый флаг, иначе регресс не поймаем.

### 1.3 Что не трогать в этапе 1

- `PAGE_SIZE_MODEL_NODES = 25000` и `Promise.all` по всем страницам — это этап 2. После 1.1 страниц станет ~5, очередь ослабнет сама.
- Реактивность 104k объектов и ленивое дерево — не здесь.
- Формат API списков нод/связей/диаграмм.

## Этап 2. Размер страницы, параллелизм, главный поток

Цель: страница не блокирует вкладку на 8–21 с и не запирает шесть HTTP-соединений. Полная модель всё ещё в памяти.

### 2.1 Параллелизм страниц

`fetchAllByModelId` после страницы 0 не должен выпускать все оставшиеся сразу.

- Страница 0 — как сейчас, чтобы узнать `totalPages`.
- Остальные — пул с потолком **4** одновременных запроса (константа рядом с page size).
- На HTTP/1.1 (6 слотов) остаются 2 слота для блокировок, каталога, WS upgrade.
- Дедуп по `id` и запасной последовательный обход при неизвестном `totalPages` сохраняются.

Тест: при `totalPages = 10` в полёте не больше 4 запросов одновременно (счётчик + искусственная задержка в моке).

### 2.2 Размер страницы

Потолок сервера оставить 25000 — запас для импорта и разовых выгрузок.

Клиентский размер для редактора — отдельная константа, не обязательно равная потолку. Стартовое значение **8000** (между 2000 с очередями и 25000 с паузами главного потока). Подбирается замером на эталонной модели:

- время ответа страницы `/nodes` и `/links`;
- длина long task на `JSON.parse` + `toEditorNode` / `toEditorLink`;
- очередь `/diagram-locks` во время обхода.

Критерий выбора: long task на одну страницу < 2 с, ответ бэка `/nodes` < 4 с, `/diagram-locks` не ждёт больше 1 с. Если 8000 не проходит — шаг 5000, не возврат к 2000 без лимита параллелизма.

`PAGE_SIZE_MODEL_DIAGRAMS = 2000` не менять: 8k диаграмм и так 4 страницы, `attrs` на shell уже выключены.

`mapInChunks` (500 + `setTimeout(0)`) оставить. При необходимости уменьшить чанк, если 8000 строк всё ещё рвут кадр.

### 2.3 Реактивность (если дерево после этапа 1 всё ещё пустое)

Виртуализатор рисует только видимые строки, но `state.nodes = 104720` прокси-объектов Vue вешает главный поток на присвоении. Если после этапа 1 корни не появляются, а куча растёт — вынести `nodes` / `links` / `diagrams` в `shallowRef` (или `markRaw` на элементах) и обновлять индексы (`Map` по id, дети по parent) явно.

Это не ленивая загрузка: данные те же, нет глубокой реактивности на 100k строк. Делать только по факту замера, не заранее. Отдельного API не требует.

## Этап 3. Ленивая загрузка

Отдельный этап дорожной карты. Пока редактор держит все ноды и связи в памяти, корпоративная модель упрётся в лимит вкладки независимо от сети.

### Зачем

Этапы 1–2 режут трафик и очереди примерно вдвое и убирают ложные простои. Они не убирают 1,8 ГБ и не гарантируют живое дерево на 104k нодах. Нужна загрузка по требованию.

### Целевое поведение

1. **Дерево.** При открытии модели — корни (ноды с `parent_node IS NULL`) + папки, у которых нужно показать шеврон. Раскрытие папки — дети этой папки. Поиск по дереву — серверный, не клиентский обход 104k.
2. **Диаграммы.** Список без `attrs`, как сейчас. Полный документ — при открытии (`GET /diagrams/{id}`), как уже делает гидратация `_attrsPending`.
3. **Связи.** Не грузить все 170k при открытии. Для открытой диаграммы — связи её экземпляров. Для трассировки / матрицы — отдельный запрос по конечным точкам или по диаграмме.
4. **Live sync.** Полный `fetchAllByModelId` на каждое событие запрещён. Применять гранулярные события (`parseGranularSyncEventsFromPayload` уже есть) или точечный `GET` по id. Полный pull — только явная команда «подтянуть с сервера».
5. **Сохранение.** `batch-save` уже шлёт дельту. Клиентский стейт должен уметь жить с неполной коллекцией: не считать «нет в массиве» удалением при merge.

### API, которого сейчас нет

`GET /nodes` фильтрует по `modelId` / `ownerId` / `name`, без родителя. Для дерева:

| Параметр | Смысл |
|---|---|
| `parentId` | дети этой ноды; пустое/`root` — корни модели |
| `foldersOnly` | опционально, только Directory, чтобы нарисовать шевроны без всех листьев |

Нужны стабильная сортировка (как `findByModelIdOrdered`: parent, `treeOrder`, id) и `totalElements` на уровне родителя — чтобы показать «ещё N», если детей больше страницы.

Поиск: уже есть `SearchService` / `GET` с `name=`. Дерево при непустом запросе должно ходить туда, а не строить `treeRows` по полному массиву. Лимит `MAX_SEARCH_TREE_ROWS` остаётся клиентским предохранителем.

Связи: либо `?diagramId=`, либо `?sourceId=` / `?targetId=` (часть уже есть). Для холста достаточно связей, чьи концы есть среди `instances` открытой диаграммы.

Ответ списка — тот же `Page` (`content` + `page`). Новые параметры только добавляются.

### Клиентский стейт

Не `nodes: EditorNode[]` как единственный источник. Нужны:

- индекс по id;
- индекс детей по `parentId` (и флаг «дети ещё не грузились»);
- множество загруженных id.

`mergeEntityListFromRemote` сегодня при полном снимке вычищает отсутствующие строки. На неполном снимке это сотрёт нераскрытые ветки. Merge этапа 3 — только по явным create/update/delete или по загруженной ветке.

Открытие диаграммы по URL (`?diagramId=`) должно само догрузить путь в дереве до предка диаграммы и гидратировать attrs.

### Вне скоупа этапа 3

- Перенос каталога нотации на ленивую загрузку (он маленький).
- Ленивый импорт OEF / package — у импорта свой пайплайн.
- Сжатие или проекция полей `NodeResponse` (отдельный разговор, если этап 3 всё ещё тяжёл).

Этап 3 получает собственный implementation plan, когда до него дойдёт очередь. Этот документ фиксирует только контракт и границы.

## Порядок работ

1. Этап 1 в `arepos-server` и `warchi` на ветке `feat/large-model-editor-load`. Papirus не нужен, `file:../papirus` не переключать.
2. Прогон юнит-тестов: page size на бэке; live sync не вызывает `fetchAllByModelId` на `ws_connect` / `session_resync` после `whenBackgroundReady`; `stomp_model_changed` по-прежнему тянет.
3. Замер на эталонной модели: число запросов `/nodes`, отсутствие второго обхода, `/diagram-locks` без многосекундной очереди.
4. Этап 2 по результатам замера (сначала пул, потом константа page size).
5. Этап 3 — отдельный документ и ветка, когда этапы 1–2 влиты.

## Риски

| Риск | Что делаем |
|---|---|
| Снятие аннотации ломает форму `Page` | `serialization-mode: via_dto`; смоук списка нод/моделей; фронт читает и `content`, и обёртку `page` |
| Пропущенный `model_changed` за долгий load | очередь события до `whenBackgroundReady`; не лечим полным pull «на всякий случай» |
| Режим `poll` перестанет обновлять модель | после фона таймер работает как сейчас; запрещён только немедленный pull на старте |
| 25 000 после этапа 1 снова вешает вкладку | этап 2 сразу после замера, не ждать этапа 3 |
| `shallowRef` сломает вотчеры по полям ноды | только если замер покажет, что реактивность — узкое место; точечно проверить dirty/rename/tree |
| Неполный стейт этапа 3 сломает merge и batch-save | отдельный план; `mergeEntityListFromRemote` нельзя оставлять в режиме «полный снимок» |
