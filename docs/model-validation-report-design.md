# Встроенный отчёт валидации модели и схлопывание дубликатов

Дата: 2026-08-22  
Репозитории: `warchi`, `arepos-server`  
Ветка (когда дойдёт до реализации): `feat/model-validation-report`

## Цель

Дать в модели отдельный отчёт по дубликатам дерева — без выгрузки всего графа
в браузер и без пользовательского JS на полном снимке.

Пользователь открывает модель, нажимает кнопку рядом с матрицей связей и видит
группы дубликатов экземпляров и связей. В группе можно посмотреть, на каких
диаграммах стоит каждый член, выбрать кого оставить и схлопнуть пару атомарно
на сервере.

## Зачем не скрипты

Диаграммные скрипты остаются в браузере: их контекст — открытый холст.

Скрипты со скоупом «вся модель» в v1 не делаем. Произвольный JS по дереву
потребовал бы отдельный runner; для двух конкретных проверок это избыточно.

Отдельные API-ключи для этого отчёта не нужны. Доступ — cookie-сессия и право
на модель (просмотр для GET, редактирование для merge), как у матрицы.

## Границы v1

Входит:

- две проверки: дубликаты узлов и дубликаты направленных связей;
- страница отчёта в модели;
- мастер слияния одной пары (узел или связь);
- атомарные write API на arepos;
- sync-события merge в том же формате, что batch-save.

Не входит:

- пользовательские скрипты по всему дереву и отдельный JS-runner;
- нечёткий поиск по имени;
- слияние всей группы разом;
- проверка «связь недопустима нотацией»;
- перенос wiki / `documentFileId` / `document_refs` с удаляемой сущности;
- service account / генерация ключей в админке.

В выборку не входят soft-deleted ноды, связи и диаграммы (`deleted = true`).

## Правила совпадения

### Узлы

Дубликат — два и более узла одной модели с одним `nodeTypeId` и одним именем
после `trim` без учёта регистра.

Тип с именем `directory` (без учёта регистра) не участвует. В продукте только
Directory может быть родителем в дереве; обычный компонент — лист.

Имя группы в API — имя первого члена после сортировки по `id ASC` (как в дереве,
без lowercase). Ключ группировки на сервере — `nodeTypeId + lower(trim(name))`.

### Связи

Дубликат — два и более ребра с одним `sourceId`, одним `targetId` и одним
`linkTypeId`. Направление учитывается: `A→B` и `B→A` одного типа — не дубликат.

## Контракт отчёта

`GET /api/v1/models/{id}/validation-report`

Право: просмотр модели. Read-only, без attrs.

Сервер считает две проверки SQL `GROUP BY` по проекции (`id`, имена, типы,
концы связи, родитель). `attrs` и полный граф в JSON не выгружаются.

```json
{
  "modelId": "…",
  "generatedAt": "2026-08-22T12:00:00Z",
  "duplicateNodes": [
    {
      "nodeTypeId": "…",
      "nodeTypeName": "Application Component",
      "name": "CRM",
      "count": 2,
      "nodes": [
        {
          "id": "…",
          "name": "CRM",
          "parentId": "…",
          "parentName": "Applications"
        }
      ]
    }
  ],
  "duplicateLinks": [
    {
      "sourceId": "…",
      "sourceName": "A",
      "targetId": "…",
      "targetName": "B",
      "linkTypeId": "…",
      "linkTypeName": "Serving",
      "count": 2,
      "links": [{ "id": "…" }]
    }
  ]
}
```

`parentId` / `parentName` — папка в дереве; оба `null`, если родитель — корень
или системный tree root. Клиент не догружает дерево ради подписи папки.

Все группы возвращаются. Если в группе больше 50 членов, в массиве первые 50
(сортировка `id ASC`) плюс поле `count` с полным размером. Merge вызывается по
id, а не по индексу в усечённом списке.

Диаграммы в отчёт не кладём. При раскрытии члена клиент вызывает
`GET /api/v1/models/{modelId}/diagram-references`. Endpoint принимает ровно один
из параметров: `nodeId` или `linkId`. `linkId` возвращает неудалённые диаграммы,
в attrs которых есть edge с этим `modelLinkId`.

Ответ пагинирован (как сейчас, default size 50). Клиент листает, пока
`last !== true`. Preview (ниже) отдаёт полный список id диаграмм для пары
keep/drop, чтобы мастеру не собирать страницы самому.

## Preview мастера

Клиент не собирает инцидентные связи A/B сам.

`GET /api/v1/models/{id}/validation/merge-nodes-preview?keepId=&dropId=`  
`GET /api/v1/models/{id}/validation/merge-links-preview?keepId=&dropId=`

Право: просмотр модели.

`400`, если `keepId == dropId` или пара не является дубликатом по правилам выше.

Preview узлов возвращает:

- только `typeProperties` keep и drop — не `treeOrder`, не `notationComponents`,
  не `componentProperties`, не `documentFileId`;
- уникальные связи drop (id, тип, направление, другой конец);
- matching-связи drop и связи keep↔drop — одним списком `linksToDelete`
  (только для текста «будут удалены», не для выбора);
- число diagram instance у каждого и полный список `{ diagramId, diagramName }`;
- `hasChildren` — есть ли у drop дочерние ноды;
- `hasDocuments` — у drop задан `documentFileId` в attrs;
- `diagramsToReparentCount` — число диаграмм с `node_id = drop`.

Preview связей возвращает только `typeProperties` обеих связей и полный список
диаграмм, где стоит каждое ребро.

**Уникальная связь drop:** после подстановки `drop→keep` не существует связи
keep с тем же `linkTypeId`, тем же вторым концом и тем же направлением.

- `drop→X` уникальна, если нет `keep→X` того же типа;
- `X→drop` уникальна, если нет `X→keep` того же типа;
- `keep↔drop` в уникальные не входят.

**Matching-связь drop:** после подстановки уже есть такая связь у keep.
Её нельзя переносить: получится новый дубликат. Всегда удаляется.

## Что меняется в attrs

У ноды и связи attrs — составной объект. Merge не принимает и не перезаписывает
его целиком.

POST несёт только итоговые `typeProperties`. Сервер записывает их в keep и
оставляет у keep без изменений: `treeOrder`, `notationComponents`,
`componentProperties` / `notationRelations`, `relationProperties`,
`documentFileId`.

`documentFileId` и wiki drop в v1 не переносятся. В таблице свойств мастера
этого поля нет. `document_refs` с `node_id = drop` при удалении ноды станут
`NULL` (текущий FK).

Component properties фигурки остаются на diagram instance.

## Правила merge узла

Пользователь выбирает keep (A) и drop (B), по одной паре за раз.

1. Итоговые `typeProperties` A — пополевый diff в мастере. Совпадающие поля
   свёрнуты.
2. Уникальные связи B: пользователь отмечает, какие перенести.
   Перенос — `UPDATE` концов этой же связи (`drop` заменяется на `keep`),
   id связи сохраняется, диаграммные рёбра этой связи не переписываются.
3. Все остальные инцидентные связи B удаляются вместе с их edge instance:
   - уникальные, не попавшие в `transferLinkIds`;
   - matching (`B→X` при уже существующем `A→X` того же типа и наоборот);
   - связи `A↔B` (петель `A→A` не создаём).
4. Diagram instance с `modelNodeId = B` получают `modelNodeId = A`.
   Если A и B были на одной диаграмме, остаются две фигуры экземпляра A
   (это уже допустимо в редакторе).
5. Диаграммы с `node_id = B` получают `node_id = A` (в дереве переезжают под A).
   Не полагаться на `ON DELETE SET NULL` — иначе диаграммы молча уйдут в корень.
6. A остаётся в своей папке и со своим именем (орфография A). B удаляется.
7. Если у B есть дочерние ноды — отказ `400`. В продукте у компонента детей нет;
   защита на случай импорта/MCP. Диаграммы на B — не дети, их перевешиваем (п. 5).
8. Если `hasDocuments` — предупреждение на шаге подтверждения, не отдельный
   диалог: документация B будет потеряна.
9. Нужно право редактирования модели.

## Правила merge связи

1. Итоговые `typeProperties` оставшейся связи — тот же пополевый diff.
   `notationRelations` и `relationProperties` keep не трогаем.
2. Diagram edge, ссылавшиеся на drop, переписываются на keep.
   Два ребра на одном холсте после схлопывания ссылаются на одну связь.
   UI и так не даёт вручную положить второе ребро того же `modelLinkId`
   (`alreadyOnDiagram`) — после merge это только просмотр уже лежащих рёбер.
3. drop удаляется.

## Write API

Право: редактирование модели.

`POST /api/v1/models/{id}/validation/merge-nodes`

```json
{
  "keepId": "…",
  "dropId": "…",
  "typeProperties": {},
  "transferLinkIds": ["…"],
  "keepUpdatedAt": "…",
  "dropUpdatedAt": "…"
}
```

`POST /api/v1/models/{id}/validation/merge-links`

```json
{
  "keepId": "…",
  "dropId": "…",
  "typeProperties": {},
  "keepUpdatedAt": "…",
  "dropUpdatedAt": "…"
}
```

`typeProperties` — полный итоговый объект свойств типа, не patch всего attrs.
Пустой `transferLinkIds` допустим: все уникальные связи B удаляются.

Сервер в одной транзакции:

- отвергает `keepId == dropId` (`400`);
- проверяет, что пара всё ещё дубликат;
- сверяет `updatedAt` keep/drop (несовпадение → `409`);
- проверяет, что каждый `transferLinkId` — уникальная связь drop (иначе `400`);
- применяет правила выше;
- если любая затрагиваемая диаграмма заблокирована **другим** пользователем —
  `409` с той же семантикой lock, что batch-save / diagram-lock;
- пишет `ModelSyncEntityEvent` того же вида, что batch-save: delete drop,
  update keep, update/delete затронутых связей, update затронутых диаграмм.
  Одного bump `updatedAt` недостаточно: открытый редактор коллеги слушает outbox.

Клиент не патчит граф и диаграммы сам.

## UI

Маршрут: `/models/:id/validation` (`model-validation`).  
Кнопка в `ModelEditorHeader` рядом с матрицей (`grid_view`).

Несохранённые правки в редакторе уже блокируют уход (`onBeforeRouteLeave`) —
отдельный guard не нужен.

Шапка как у матрицы: назад в редактор этой модели, имя модели, заголовок
«Валидация».

Страница не вызывает `loadModelEditorData`. Только report + ленивые references
+ preview при открытии мастера.

Возврат в редактор (`/models/:id`) — обычный mount и загрузка с сервера.
B на клиенте не остаётся: страница отчёта граф не кэширует.

Состояния: загрузка, ошибка, пусто (дубликатов нет), две секции «Экземпляры»
и «Связи» с числом групп.

Карточка группы узлов: тип + имя + бейдж `N копий`. Внутри — члены, подпись
папки из `parentName`, чипы диаграмм (после догрузки references). Пользователь
отмечает keep; у остальных — «Слить в выбранный».

Карточка группы связей: `A → B · Serving · N копий`, тот же выбор survivor.

Клик по чипу диаграммы открывает редактор как обычное открытие холста:
`/models/:id?diagramId=…&nodeId=…` или `…&linkId=…`, с lock диаграммы и фокусом
на сущность после догрузки scope.

Клик по имени узла без диаграммы — `/models/:id?nodeId=…`: догрузить путь в
дереве и выделить узел, диаграмму не открывать, lock не брать.

Мастер — модалка на странице отчёта, не отдельный роут.

1. Свойства: таблица поле `typeProperties` / A / B / итог. `documentFileId` нет.
2. Связи (только узлы): уникальные связи B — перенести или нет; текст что
   matching и A↔B удалятся; сколько диаграмм переедет с B на A.
3. Подтверждение: кто останется, кто удалится, сколько instance будет
   переписано, предупреждение про documents B. Затем POST.

Успех: тост, закрыть модалку, заново запросить report.  
`409`: не повторять merge молча; предложить обновить отчёт.

Диаграммные скрипты и их модалка в редакторе не меняются.

## Ошибки

| Ситуация | Ответ |
|---|---|
| Нет права просмотра | 403 на GET |
| Нет права редактирования | 403 на POST |
| `keepId == dropId` / пара не дубликат / чужая модель / Directory | 400 |
| У `drop` есть дочерние ноды | 400 |
| `transferLinkIds` не из уникальных связей `drop` | 400 |
| `updatedAt` keep/drop разошёлся | 409 |
| Диаграмма заблокирована другим | 409 lock |
| `drop` уже удалён | 409 |

## Проверка

arepos-server:

- grouping узлов (trim + case, Directory и `deleted` вне выборки);
- grouping связей (направленный);
- `diagram-references?linkId=` (ровно один из `nodeId`/`linkId`);
- merge узлов: перенос уникальной связи с сохранением id; удаление matching
  и A↔B вместе с edge instance; remap instance (две фигуры A на одной
  диаграмме); reparent `diagrams.node_id`; удаление B; отказ при детях-нодах;
  `typeProperties` не затирает прочие ключи attrs; 409 по `updatedAt` и lock;
  outbox-события как у batch-save;
- merge связей: remap edge, `typeProperties` only, два ребра keep на одной
  диаграмме.

warchi:

- кнопка и маршрут;
- сборка групп и мастер (выбор keep/drop, diff `typeProperties`, transfer);
- листинг всех страниц `diagram-references`;
- после успеха отчёт обновляется;
- возврат в редактор грузит состояние с сервера, без полного snapshot «на всякий
  случай»;
- клик по чипу открывает диаграмму; клик по имени — только дерево.

i18n: все строки `ru` и `en` в `src/i18n/messages.ts`.

## Связь с уже существующим

- Паттерн навигации — как `/models/:id/relation-matrix`, но без клиентского
  full-load.
- `findDuplicateLinks` в диаграммных скриптах не удаляем: это другой скоуп.
- Будущий JS-runner для модельных скриптов этим отчётом не блокируется и не
  требуется для v1.
