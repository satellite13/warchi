# Версионирование нотации: компоненты и связи

При создании новой версии нотации встаёт вопрос: нужно ли поднимать версии компонентов и связей (relations) или делать copy-on-write для изменяемых, выставляя им версию, равную версии нотации.

## Как сейчас

- **Компоненты и связи** привязаны к нотации по **id нотации** (FK). Уникальность: `(notation, name, version)`.
- **Новая версия нотации** возможна двумя путями:
  1. **PUT нотации** — меняется версия **в той же записи** (тот же id). Все компоненты/связи остаются привязаны к этому id, их версии не трогаются.
  2. **POST copyNotation (sourceId)** — создаётся **новая запись** нотации (новый id, новый name/version), затем **копируются** все компоненты и связи в эту новую нотацию. У копий **не меняют** `version` — остаётся как у источника (например, 1.0.0). В итоге нотация 1.1.0 может содержать компоненты со version 1.0.0.

Отдельного эндпоинта «создать новую версию нотации» (аналог baseline у диаграммы) в API нет; по смыслу эту роль выполняет copyNotation.

## Нужно ли поднимать версии / делать copy-on-write

Да, это имеет смысл. Два варианта:

### 1. При создании новой версии нотации поднимать версии (или выравнивать)

При **copyNotation** (или будущем «create new version») у скопированных компонентов и связей задавать **version = version новой нотации**.

- **Плюсы**: версия нотации и версии её компонентов/связей совпадают, проще понимать «срез 1.1.0», проще сравнивать версии.
- **Реализация**: в коде копирования после `srcComponent.copy(..., notation = newNotation, ...)` добавить `version = newNotation.version` (и то же для Relations). Уникальность `(notation, name, version)` не ломается: нотация уже другая.

### 2. Copy-on-write для изменяемых

Не копировать компоненты/связи при создании новой версии нотации. Новая версия нотации изначально «пустая» или ссылается на те же сущности. При **первом изменении** компонента/связи в контексте новой нотации — копировать эту сущность, привязать к новой нотации и выставить ей **version = version нотации**.

- **Плюсы**: меньше дублирования, не трогаем то, что не редактировали.
- **Минусы**: сложнее модель (нужно хранить/разрешать «наследование» от предыдущей версии нотации, или явно различать «общие» и «свои» компоненты/связи), сложнее API и UI.

## Рекомендация

- **Сейчас** проще и предсказуемее: при создании новой версии нотации (в т.ч. в `copyNotation`) **поднимать/выравнивать версии** — у всех скопированных компонентов и связей выставлять **version = newNotation.version**. Так «новая версия нотации» = цельный срез с согласованными версиями компонентов и связей, без смены модели данных.
- **Copy-on-write** имеет смысл рассматривать позже, если появятся большие нотации и станет важно не копировать десятки неизменённых компонентов при каждом создании версии.

## Где менять (arepos-server)

- **NotationsController.kt**, метод `copyNotation`: при сохранении копий компонентов и связей добавить в `.copy()` поле `version = newNotation.version` (для Components и Relations), чтобы скопированные сущности получили версию новой нотации.
